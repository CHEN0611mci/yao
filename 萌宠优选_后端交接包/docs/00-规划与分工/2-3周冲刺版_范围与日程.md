# 2–3 周冲刺版：里程碑/范围/分工（模板基座方案）

> 前置决策（已确认）：**期限 2–3 周**、**基于 RuoYi-Vue 模板基座二次开发**、4 人技术底子不确定。
> 本文是 [小组作业实施流程与分工方案.md](小组作业实施流程与分工方案.md) 的**压缩执行版**；冲突时以本文的"3 周日程表"为准。
> **核心判断：3 周做不出教材全流程 + 全部企业级能力。必须承认这一点，把分数压在"能跑 + 有留痕 + 能复现"上。**

## A. 3 周版范围冻结（比 7 周版砍掉约 40%）

### A.1 必做（Must）——缺一项就掉档

| # | 内容 | 为什么不能砍 |
|---|---|---|
| M1 | 基座跑通：RuoYi 导入 SQL + Redis + 前后端可登录 | 一切演示的前提 |
| M2 | 会员体系：注册/登录（Token 存 Redis）、`@MemberLogin` 拦截器 | 无登录 = 无权限演示 |
| M3 | 商品：分类 + 商品/SKU + 图片 + 上架审核 | 商城脸面 |
| M4 | 购物车 → 结算 → 下单（`@Transactional` + **原子扣减防超卖**） | 业务闭环核心，防超卖是评分点 |
| M5 | 模拟支付沙箱（成功/失败/**超时**）+ **回调幂等** | 教材只有"弹框改状态"，你们补上就是差异化 |
| M6 | 订单六状态页签 + 取消/确认收货 | 顺序图演示 |
| M7 | RBAC 权限拦截 + **审计日志** | 评分表"安全"最便宜的得分点 |
| M8 | **测试证据**：单元测试（核心 Service）+ 并发防超卖测试 + 覆盖率报告 + 一份 k6/JMeter 压测（QPS/RT/错误率） | 无测试 = 低分 |
| M9 | **一键启动**：docker-compose 或 start 脚本 + README + 测试账号 + 初始化数据 | 评分表"可复现"硬指标 |
| M10 | **AI 日志 ≥30 条**（Prompt + 采纳理由 + 人工修改 + 测试结果） | 最容易丢分的项 |
| M11 | 三份文档 + PPT + ≤15 min 视频（含录屏） | 交付物本身 |

### A.2 明确砍掉（写进文档的"未做/后续规划"里，主动说明比被评委问出来好）

- ✂ 售后工单、评价、结算/对账、财务角色
- ✂ 秒杀、优惠券、推荐、多租户、灰度发布
- ✂ Kafka、Nacos、Spring Cloud Gateway、K8s（保留"架构预留说明"即可）
- ✂ ELK、链路追踪（用 traceId 日志 + Grafana 截图替代）
- ✂ E2E 全量自动化（只做 1 条主干 Playwright 用例，或改人工录屏代替）
- ✂ 客服/仓库/运营独立后台（角色用 RBAC 造数据展示，不建完整后台）

> **砍范围的红线**：M1–M5 任何一项在第 2 周末还没跑通，就再砍 M9 的 docker-compose（退化为"录制一键启动脚本 + 录屏"）——**但 M8 测试和 M10 AI 日志绝不允许砍**，它们是评分表直接项。

## D. 技术底子不确定时的"防崩"三条

1. **每个模块先要"能跑的丑版本"，再美化**：D6 之前所有页面允许丑，但不允许跑不通。
2. **一切以录屏证据为准**：功能做完立刻录 30 秒；不要等到最后一天才发现环境坏了。
3. **基座之上的自研点必须能说清**：至少准备 3 个"我们改了什么/为什么"（防超卖、幂等、超时关单），这是把"套模板"变成"二次开发"的关键。

## E. 3 周版的 5 个演示场景（视频里逐个录，替代 7 周版的 8 个）

1. 主闭环：登录 → 搜索 → 详情 → 加购 → 下单 → 沙箱支付 → 商家发货 → 确认收货（**录屏，含数据库库存变化**）
2. 权限拦截：会员访问管理接口 → 403，审计日志新增一条；无权限按钮不可见
3. 防超卖：库存 1，20 并发下单 → 仅 1 单成功（跑测试类，展示控制台 + 数据）
4. 幂等 + 超时关单：同一回调重放 3 次只生 1 笔；未支付订单 15 分钟后自动关闭并回滚库存
5. 压测与监控：k6/JMeter 报告（QPS、RT、错误率）+ Grafana 大盘截图（含 Redis 缓存前后对比）
