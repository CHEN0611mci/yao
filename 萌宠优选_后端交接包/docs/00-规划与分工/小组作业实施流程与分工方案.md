## 0. 先看清评分逻辑（决定后面所有取舍）

| 评分档 | 判定标准 | 含义 |
|---|---|---|
| 低分 | 只有增删改查 / 无权限 / 无测试 / 无部署 / 无监控 / 无 AI 记录 | 【红线】这 6 项每一项都是扣分项，不是加分项 |
| 基本 | 功能完整且能运行 | 及格线 |
| 高分 | 企业级架构 + 安全 + 性能 + 测试 + 部署 + 监控 + **AI 可复现记录** | 目标档 |
| 创新 | 秒杀 / 优惠券 / 分布式事务 / 灰度发布 / 链路追踪 / 多租户 | 冲 90+ 用，非必需 |

**一句话战略**：把 70% 的精力花在「**可复现、可截图、可演示**」上——因为所有高端能力都要靠 *截图 + 测试报告 + AI 日志* 变成分数。没有留痕的企业级能力 = 0 分。

交付物只有 3 样（别做偏了）：
1. **一个压缩包**：源码 + 数据库脚本 + 部署脚本
2. **三个文档**：企业级需求文档、设计文档、测试报告
3. **一份 PPT + 一段 ≤15 分钟录屏视频**（必须录屏演示：系统运行、权限拦截、异常流程、监控/压测结果；不能只放 PPT）

## 1. 第一步：选题与范围冻结（必须第一天定死）

### 1.1 领域推荐：**校园二手交易商城**（备选：社区生鲜、校园图书）

理由：业务闭环天然完整（发布→审核→下单→支付→发货→确认→评价→售后→提现），有「库存唯一性/防超卖」「商家角色」「风控审核」等天然企业级素材，且**没有生鲜的冷链、医药的资质门槛**，4 人 6~7 周可控。

项目名建议：**「跳蚤街 · 校园二手商城」**（名字必须出现在文档/PPT/系统标题里，否则评委会扣"项目立意"分）。

### 1.2 角色权限设计（权限矩阵直接进需求文档）

| 角色 | 关键权限 | 演示价值 |
|---|---|---|
| 游客 | 浏览、搜索、看详情 | 基础 |
| 会员（买家） | 下单、支付、确认收货、评价、售后申请、成为卖家 | 主流程 |

### 1.3 范围冻结（MoSCoW）—— 先把"不做什么"写下来

**必须做（Must，验收的底线）**
1. 注册/登录/JWT 鉴权/RBAC 权限拦截
2. 商品：分类、搜索（关键词+条件）、详情、SKU/库存
3. 购物车（增删改、选中结算）
4. 下单：地址、金额计算、**库存扣减（防超卖）**、订单状态机
5. **支付沙箱**（模拟支付成功/失败/超时回调）+ 超时未支付自动关单
6. 订单履约：发货、确认收货、售后申请/审核、评价
7. 商家后台：商品发布与上下架、订单管理
8. 运营/管理后台：商品审核、用户管理、审计日志
9. 统一 Result 返回、统一异常、统一分页、统一 traceId 日志、OpenAPI 文档
10. 一键起：docker-compose（MySQL+Redis+RabbitMQ+后端+Nginx+前端）+ 初始化 SQL + 测试账号
11. 单元测试 + 集成测试 + E2E + 压测报告 + 监控截图
12. AI 全流程日志（≥40 条高价值记录）

**应该做（Should）**：秒杀/限时特价、关键词搜索优化、Redis 热门商品与分类缓存、接口限流、审计日志可视化。
**可以做（Could）**：优惠券、推荐（"猜你喜欢"）、延迟队列自动评价。
**明确不做（Won't，写进文档，防止评委会问）**：真实支付对接、多租户、K8s 集群、微服务拆分（说明"以 Nacos/Gateway 预留"即可）。

> **教材"支付"的最大缺口（务必在你们的文档里点出来，这是差异化得分点）**：教材的模拟支付只是"弹框 → 前端点头 → 后端把订单改成已支付"，**没有**支付回调验签、**没有**幂等、**没有**超时未支付关单与库存回滚、**没有**对账。你们要在同样简化的沙箱里补上这四件事（见 1.6 场景 5、6），并在视频"关键难点"部分明确对比"教材做法 vs 我们的做法"。

### 1.5 关键决策①：自己搭 vs 基于若依（RuoYi）——第 1 天必须定

| | 方案 A：自建 Spring Boot 3 + Vue3 骨架 | 方案 B：基于 RuoYi-Vue-Plus 二次开发（**推荐**） |
|---|---|---|
| 起点 | 空仓库，公共层全自己写 | 自带 RBAC、代码生成、审计日志、Redis、Quartz、监控、多数据源 |
| 前 2 周风险 | 高：可能还在配权限拦截 | 低：第 1 天就能登录后台、分配权限 |
| 评分表覆盖 | 全自研，架构讲述更有说服力 | 需明确"哪些是自己实现的"，否则显得像套模板 |
| 适配 4 人 6–7 周 | 勉强 | **匹配**（教材 9.2 走的就是这条路） |

**结论**：选方案 B，但必须守住三条底线，否则会从"高分"掉进"低分"：
1. **不许"下载即交付"**：在若依之上必须自研差异化能力——防超卖、接口幂等、支付沙箱+超时关单、压测报告、Grafana 大盘、AI 日志体系。
2. **文档里要有一张"自研 vs 复用"对照表**（哪张表、哪个接口、哪段代码是自己写的），并在视频里讲清改造点。
3. **改动要能讲出"为什么"**（如：若依默认无下单事务/幂等，我们如何补），这就是评分表说的"关键决策留痕"。

### 1.6 必须准备好的 8 个演示场景（视频里逐个录）

1. 完整下单闭环（含库存 10 → 9 的数据库变化）
2. 权限拦截：会员直接访问 `/api/admin/**` → 403 + 审计日志新增一条
3. 越权拦截：商家 A 修改商家 B 的商品 → 403

5. 幂等：同一 `Idempotency-Key` 重复提交支付回调 → 只生成 1 笔
6. 异常流程：支付超时 → 延迟队列自动关单 + 库存回滚
7. 性能：压测前后对比（无缓存 vs Redis 缓存）QPS/RT 截图 + Grafana 曲线
8. AI 复现：现场让 AI 改一个需求，展示 Prompt → 生成 → Review → 测试通过的全过程

## 2. 组织与分工：按**业务域纵切**，不按"前端/后端"横分

> 4 个人最致命的坑：2 人写后端、1 人写前端、1 人等接口 → 第 4 周全员卡住。

## 3. 工程基线：第 1 周必须冻结，之后不许改

### 3.1 技术栈（附选型理由 + 替代方案 + 风险 —— 这是文档必答题）

> 若采纳 **1.5 方案 B（RuoYi-Vue-Plus 基座）**：以下"后端框架/鉴权/文档/定时任务/权限模型"由基座提供，你们的工作量集中在**业务域 + 企业级加固 + 留痕**。
> 风险提示：RuoYi 社区版基于 Spring Boot 2.x + JDK 8；**RuoYi-Vue-Plus** 才支持 Spring Boot 3.x + JDK 17。选型时按团队 JDK 环境二选一，并在设计文档写明版本。

| 层 | 选型 | 为什么选 | 替代方案 | 风险与对策 |
|---|---|---|---|---|
| 后端 | Spring Boot 3.2 + JDK 17 + MyBatis-Plus | 资料多、AI 生成质量最高、团队最易上手 | .NET 8 / Go(Gin) | 启动慢 → 本地热部署、分层清晰 |
| 前端 | Vue 3 + Vite + TypeScript + Element Plus + Pinia | 组件全、后台页面开发快 | React + AntD | TS 报错拖进度 → 只在接口层强类型 |
| 数据库 | MySQL 8.0 | 事务、索引、成熟 | PostgreSQL | 并发锁 → 用 `UPDATE ... WHERE stock >= n` 原子扣减 |
| 缓存 | Redis 7 | 热点缓存 + 分布式锁 + 限流 | Caffeine(单机) | 缓存一致性 → 先更新 DB 后删缓存 + 短 TTL |
| 消息队列 | RabbitMQ 3.13 | 延迟队列插件直接做"超时关单"，比 Kafka 轻 | Kafka / RocketMQ | 消息丢失 → 手动 ack + 本地消息表 |
| 网关/静态 | Nginx | 反向代理 + 前后端分离部署 | Spring Cloud Gateway | 配置错 → 提供 nginx.conf 模板 |
| 鉴权 | Spring Security + JWT(RSA/HS256) | 无状态、易演示越权 | Sa-Token / OAuth2 | Token 泄露 → 短过期 + 刷新令牌 |
| 文档 | springdoc-openapi (Swagger UI) | 一张截图就是分 | YApi | 注解遗漏 → CI 校验 |
| 测试 | JUnit5+Mockito / Testcontainers / k6 或 JMeter / Playwright | 单测-集测-E2E-压测四层 | Postman | 环境依赖 → Testcontainers |
| 可观测 | Prometheus + Grafana + Logback traceId (+ ELK 可选) | 监控截图 = 高分证据 | SkyWalking | 资源占用 → docker-compose 单机起 |
| CI/CD | GitHub Actions（或 Jenkins） | 免费、截图好看 | Jenkins | 网络 → 本地也留可复现流水线日志 |
| 容器 | Docker + Docker Compose | 一键复现 = 验收硬指标 | K8s（不做，文档说明） | 镜像大 → 分层构建 |

### 3.3 仓库与协作方式（★ 4 人分工最关键的一步）

**结论：建「私有仓库」，不要建公开仓库。**（评分只看压缩包与文档，公开仓库不加分，却带来抄袭、密钥泄露、被同学抄三重风险。）

| 平台/形态 | 私有仓库协作人数 | 结论 |
|---|---|---|
| Gitee 个人账号（社区版） | **个人账号下所有私有仓库合计 5 人协作**，公有仓库成员不限（[Gitee 配额说明](https://help.gitee.com/account/usage-quota)） | **4 人刚好够用，首选**（国内快、老师熟悉） |
| GitHub Free（个人/组织账号） | 免费已可为私有仓库添加协作者；但**组织仓库**的组织成员数受免费额度约束（[GitHub 计划说明](https://docs.github.com/en/get-started/learning-about-github/githubs-plans)） | 可用；若四人无法全部加入，改用「组织 + 邀请」或换 Gitee |
| 公开仓库 | 成员不限 | ❌ 不推荐（见右侧风险） |

**为什么不要公开仓库**
1. **泄密风险**：若依的 `application-druid.yml`、`redis` 配置里常有明文账号密码，`.env` 也可能被误提交；公开后搜索引擎/爬虫会采集。**提交前必须把密码换成占位符 + 用 `.env`（且 `.env` 进 `.gitignore`）。**
2. **抄袭风险**：小组作业公开等于把答案挂出去，一旦被其他组抄了，责任回溯到你们（且你的同学/队友可能反对）。
3. **不加分**：实验四只要求"提交源码、数据库脚本、部署脚本（一个压缩包）"，从未要求公开仓库。老师若要验证，你们给**仓库地址（私有）+ 只读邀请**或用**每个 commit 的 hash**证明提交历史即可。
4. **许可证**：若依是 MIT 许可，二次开发合法，但**必须保留其 `LICENSE` 与来源说明**，并在文档写清"基于 RuoYi 二次开发"，这反而显得规范。

**仓库创建参数（A 执行，10 分钟）**
```
仓库名：campus-mall（或 jie-jie-jie）
可见性：Private
初始化：不要勾选"添加 README/gitignore/license"（本地已有骨架时避免冲突）
分支：main（保护）+ develop（默认分支）
```
**分支保护规则（必须配，这也是"工程化"的截图证据）**
- `main`：禁止直接 push；Require pull request → 1 人 Approve；Require status checks（CI）通过
- `develop`：允许直接 push（3 周进度优先），但合并 `main` 必须走 PR

**4 人的账号与权限**
1. 仓库所有者为 A（或另开一个组织/账号持有，避免 A 一人退组导致仓库无法管理）
2. Settings → Collaborators 邀请 B、C、D，权限给 **Write**（不要给 Admin）
3. 开启 2FA（Gitee/GitHub 都建议），用 SSH key 而非密码推送
4. 建 `CONTRIBUTING.md`：分支命名、commit 规范、PR 模板（含"我改了什么/我怎么测的/AI 日志编号"三问）

**公开与私有的折中方案（推荐）**
私有仓库放全部真实代码；另建一个 **public 的 `docs-only` 仓库**，只放三个文档 + PPT + 架构图 + 脱敏后的接口清单 + AI 日志，**不放源码、不放配置、不放数据库连接串**。这样既有"可展示的专业形象"，又不承担源码泄露风险。（老师若要公开证据，给这个仓库链接即可。）

**提交前必做的 3 道密钥体检**（否则私有也不能算安全）
```bash
# 1) 全历史搜密码/密钥
git log -p | grep -iE "password|secret|accessKey|sk-|token" | head -50
# 2) 确认忽略文件生效
git check-ignore -v .env  backend/**/application-druid.yml
# 3) 若已误提交过密码：改密码 + 清历史（git filter-repo）或直接弃库重建
```
> 加分细节：`gitleaks`/`git-secrets` 挂到 CI 里，截图进设计文档"工程化"一节。
