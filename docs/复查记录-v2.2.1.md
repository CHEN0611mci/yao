# v2.2.1 复查记录

日期：2026-10-27。本机实际 API、MySQL 与 Redis 验收；前端保持 user-ui v1.2.0。

## 本轮新发现与修复

再次检查发现了多规格订单的并发死锁。原先的单 SKU 并发测试不能覆盖该场景。

- 修复前：12 个独立测试账号正序/逆序购买同商品两个 SKU，仅 5 次下单成功；跨两个商品购买四个 SKU，仅 4 次下单成功，其中一次并发取消也失败。失败接口返回 PET-5001，后端日志确认 MySQL Deadlock。失败事务回滚，测试成功订单全部取消后库存恢复。
- 原因：请求按用户提供的顺序逐个锁 SKU，并在中间更新商品销量；不同订单交叉占锁。取消按历史明细顺序回补，也存在相同问题。
- 修复：下单先按商品 ID 升序锁商品，再按 SKU ID 升序锁全部规格；商品编辑先锁商品。取消/关单按 SKU ID 升序回补。自动关单每单独立事务，避免一批订单累积持有不同顺序的 SKU 锁。
- 加锁等待后，下单使用锁定读取获得最新商品状态、价格和库存，避免 REPEATABLE READ 的旧快照用于计价。原有订单明细的显示顺序保留。

- 人为持有测试商品行锁并提交改价；等待中的下单使用新价格 1.01，订单明细金额断言通过。
- 12 个四规格订单，其中六个过期；同时运行两次关单任务、六次取消及 12 次新下单。过期订单状态 6，其余状态 5；无服务错误，所有剩余测试订单取消后库存回到 100。
- 后台商家发布、审核、权限及单 SKU 库存并发：62 项通过。
- 收藏、偏好、登录设备、手机号、地址、支付幂等：111 项通过。
- 现用数据库八项一致性检查通过；未重新初始化或重置种子数据。
- 后端 Maven 打包通过（项目未配置 Java 单元测试，本轮依据实际集成测试验收）。

证据：`verify/multi-sku/before-fix.json`、`verify/multi-sku/receipt.json`；本轮覆盖了原有会员/后台回归回执。
