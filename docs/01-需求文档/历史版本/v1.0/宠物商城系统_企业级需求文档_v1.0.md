# 1 引言

## 1.1 编写目的

本文档定义「萌宠优选 · 宠物商城系统」的企业级需求基线，回答四个问题：**为谁做、做什么、做到什么程度、如何验收**。具体用途如下：

1. **统一认知**：在 2 人团队、19 个工作日的约束下冻结范围，避免中途加需求导致主闭环延期。
2. **指导开发**：为设计文档、数据库设计、接口定义与前后端并行开发提供唯一输入；D3 冻结后接口契约"只增不改"。
3. **支撑测试**：每条功能需求均带可验证的验收标准，测试报告的用例可直接追溯到需求编号。
4. **支撑评审**：对应实验四对需求文档的硬性要求——用例图、业务流程图、领域模型、ER 图、API 清单、可验证的非功能需求，全部在本文中给出。
5. **留痕与可复现**：需求编号贯穿设计、代码、测试与演示视频，使"做了什么、为什么做、证据在哪"可被逐项核对。

本文档**不包含**：物理表结构 DDL 与索引细节（见设计文档）、技术选型论证与 ADR（见设计文档）、测试执行数据（见测试报告）。

## 1.2 项目背景

实验四要求以小组自选商城为载体，完整经历"需求分析 → 技术选型 → 架构设计 → 编码实现 → 测试验证 → 部署运维"的企业级应用全过程，并明确要求系统不能停留在课堂 CRUD 演示层面。教材第九章以「社区超市商城系统」为例给出了商品、购物车、订单、支付、后台管理的参考实现，但其支付环节仅以"弹框改状态"完成，库存扣减与异常流程也较为简化。

本项目选择**宠物用品零售**作为业务领域，原因有三：

- **业务差异清晰**：宠物商品存在"物种 / 年龄段 / 体重段 / 规格 / 保质期"等强约束属性，天然可承载"宠物档案 + 适用性筛选"这一差异化能力，避免与教材案例同质化。
- **用户痛点真实**：新手养宠人"买错粮、买错尺码、买错年龄段"是可被演示、可被验证的痛点，而非凭空构造的场景。
- **企业级能力可落地**：宠物用品的高复购、强库存属性，使"原子扣减防超卖、支付回调幂等、超时未支付关单回滚库存"成为必须解决的问题，而不是为了加分硬堆技术。

项目现有资产为 RuoYi 3.9.2 后端基座（Spring Boot 4.1.0、MyBatis、Druid、Quartz、Redis 集成、`sys_*` 权限体系）与 RuoYi-Vue3 管理前端，团队在其上做二次开发，新建 `ruoyi-mall` 业务模块与独立客户前台 `user-ui`。

# 2 项目概述

## 2.1 产品定位与命名

- **正式名称**：萌宠优选 · 宠物商城系统（Pet Mall）
- **备选名称**：毛孩子优选 / 萌宠集市（仅在名称变更时同步本文、PPT、系统标题、仓库名）
- **一句话立意**：面向养宠家庭的宠物用品零售商城，用「宠物档案 + 适用性筛选」解决"买错粮、买错尺码、买错年龄段"的核心痛点，并具备企业级交易闭环与可复现交付能力。
- **产品形态**：前后端分离的 Web 商城，含客户前台（会员购物）、商家端（发布与发货，复用后台页面按角色裁剪）、管理后台（审核、商品、订单、会员、分类、审计）。
- **市场对标**：轻量级垂直宠物电商，不追求全品类与营销玩法，追求**交易正确性、数据一致性与工程可交付性**。

## 2.2 建设目标与成功标准

### 2.2.1 目标分解

| 目标类别 | 目标描述 | 判定标准 |
|---|---|---|
| 业务目标 | 打通"浏览 → 建档 → 加购 → 下单 → 支付 → 发货 → 收货"完整闭环 | 6 个演示场景全部可现场跑通，含异常分支 |
| 业务目标 | 以宠物档案驱动选购，形成与教材案例的明确差异化 | 商品详情页可按当前会员宠物给出「适合 / 不适合」结论 |
| 工程目标 | 具备企业级架构特征：前后端分离、模块化、分层、统一规范、统一鉴权 | 端到端只通过 JSON 交互；无 JSP/Servlet 式耦合；统一 Result/异常/分页/traceId |
| 质量目标 | 交易数据一致：不超卖、不重复支付、关单必回滚 | 并发测试超卖数为 0；重复回调生效次数为 0；关单后库存与流水一致 |
| 测试目标 | 有真实可复现的测试证据 | 单测覆盖率报告、并发测试、幂等测试、k6 压测报告均可重跑 |
| 交付目标 | 换机可复现 | 按 README 在全新目录按脚本启动，完成登录与下单演示 |
| 过程目标 | AI 使用可追溯 | AI 编程日志 ≥ 30 条，每条可对应仓库代码 + 测试 + 截图 |

### 2.2.2 可验证成功标准（KPI）

| 编号 | 指标 | 目标值 | 验证方式 |
|---|---|---|---|
| KPI-01 | 主闭环可用性 | 登录→加购→下单→支付→发货→收货 全链路成功率 100%（演示 20 次无阻塞缺陷） | 演示录屏 + 缺陷记录 |
| KPI-02 | 防超卖 | 库存 1，20 并发下单，成功订单数 = 1，超卖数 = 0 | 并发测试类输出 + DB 断言 |
| KPI-03 | 支付幂等 | 同一 Idempotency-Key 重放 3 次，支付记录 1 条，订单状态只变一次 | 幂等测试用例 + 数据库查询 |
| KPI-04 | 超时关单 | 未支付订单超过阈值后自动关闭，库存回滚且流水新增 ROLLBACK 记录 | 定时任务演示 + 库存前后对比 |
| KPI-05 | 鉴权 | 未授权访问 100% 返回 401/403，且被拒请求写入审计日志 | 安全测试清单 + 截图 |

## 2.5 核心痛点与价值主张

| 痛点 | 现状（教材/通用商城） | 本系统的解决方式 | 可验证结果 |
|---|---|---|---|
| 买错粮 | 商品只有名称与价格，无适用对象说明 | 商品结构化属性（适用物种/年龄段/体重段）+ 宠物档案 + 详情页适用性判定 | 建档后在详情页得到明确"适合/不适合"结论 |
| 买错尺码/规格 | SKU 仅作价格差异展示 | SKU 规格名规范化（重量/包装/适用体重）+ 库存独立管理 | 规格与库存一一对应，售罄不可下单 |
| 超卖与"下单价变了" | 下单仅做前端校验或简单状态更新 | 单条原子 UPDATE 扣减 + `CHECK(stock>=0)` + 库存流水 + 事务回滚 | 并发测试超卖数为 0 |
| 重复支付 / 重复回调 | 无幂等设计，回调重复处理导致重复发货 | 幂等键唯一索引 + 状态机前置校验 + 唯一约束兜底 | 重放 3 次只生效 1 次 |
| 库存被"锁死" | 下单占用库存后无回收机制 | 超时未支付自动关单 + 库存回滚 + 流水记录 | 关单后库存恢复可售 |
| 越权与无留痕 | 管理接口仅登录校验 | RBAC 接口级 + 按钮级 + 资源归属校验 + 审计日志 + 脱敏 | 会员访问管理接口 403 且日志留痕 |

| 能力维度 | 教材「社区超市」做法 | 本项目做法 | 差异价值 |
|---|---|---|---|

## 2.7 产品边界

本文档定义的是**单商家平台型**（平台自营 + 商家入驻商品以 `merchant_id` 区分，不做入驻审核与结算分账）宠物用品商城。明确不做的事项见 11.1 的 Won't 清单，其中最关键的边界是：

- **不做真实支付对接**：仅沙箱模拟，不对接微信/支付宝生产接口，不处理真实资金。
- **不做售后与结算**：无退款、退货、对账、分账流程（订单取消仅覆盖"未支付"场景）。
- **不做营销玩法**：无秒杀、拼团、优惠券、满减、会员等级与积分（评价列为 Should）。
- **不做多租户与分布式部署**：单机单库单 Redis，定时任务以 Quartz 单机模式运行。

# 4 业务流程与用例

## 4.1 业务全景

本系统是一条**"以宠物档案为决策入口"的零售交易链**：游客浏览与检索商品，注册成为会员后建立宠物档案，系统据此给出适用性判断；会员将商品加入购物车、提交订单，订单在事务内完成库存扣减与快照固化；随后通过沙箱完成支付，支付结果以幂等回调落库；商家发货、会员确认收货，订单终结。与之并行的是一条**运营与治理链**：商家发布商品 → 管理员审核 → 上架销售；管理员对会员、订单实施监管，所有写操作落审计日志。另有两条**兜底链**：超时未支付自动关单并回滚库存；越权访问被拦截并留痕。

### 4.2.2 BF-05 提交订单（核心流程）

前置：会员已登录；购物车至少一条勾选行；存在有效收货地址。

1. 客户端提交 `skuId + quantity` 勾选项、`addressId`、可选 `clientToken`（前端生成的幂等键）。
2. 服务端校验登录态与地址归属（DP-01、DP-07），读取购物车勾选行。
3. 服务端查询 SKU 与商品，校验**可售条件**（BR-01）与数量上下限（BR-03）。
4. 服务端**重新计算金额**（BR-05、BR-06），不信任客户端金额。
5. 生成订单号（BR-08），写入 `pet_order`（状态 0 待付款），固化收货信息快照。
6. 对每个 SKU 执行原子扣减 `UPDATE pet_item_sku SET stock = stock - ? WHERE id = ? AND stock >= ?`；影响行数为 0 → 抛 `PET-3001`，整单回滚（BR-07）。
7. 写入 `pet_order_item` 下单快照（标题、规格、单价、数量、金额、图片）。
8. 写入 `pet_stock_log`（`type=DEDUCT`），以 `(sku_id, order_no, type)` 唯一约束防重复。
9. 删除已结算的购物车行（BR-18）。
10. 事务提交，返回订单号、应付金额、支付截止时间（下单时间 + 15 分钟）。

事务边界：步骤 5–9 处于同一 `@Transactional(rollbackFor = Exception.class)` 内；任一步失败则全部回滚，不允许出现"扣了库存没有订单"或"有订单没扣库存"。

异常处理：库存不足返回 `PET-3001`，提示具体 SKU；重复提交（同一 `clientToken`）命中唯一约束时返回已创建订单，不再新建（Should）。

### 4.2.3 BF-07 支付回调（幂等，差异化重点）

![图 4-4 支付回调幂等与超时关单时序](images/fig-4-4-seq.png)

1. 渠道（沙箱）携带 `Idempotency-Key`、订单号、金额、渠道、结果调用回调接口。
2. 服务端校验请求来源与必填参数（沙箱以内部令牌模拟签名）。
3. 尝试插入 `pet_payment`（`idempotency_key` 唯一索引）。若唯一键冲突，说明是重放：查询已有记录，**直接返回成功且不改订单状态**。
4. 校验回调金额与订单应付金额一致（BR-16），不一致记录异常并返回失败，不推进状态。
5. 结果为 SUCCESS：按状态机执行 0 → 1（待发货），写支付时间；非 SUCCESS：仅记录支付失败，订单保持待付款，可重试。
6. 记录操作日志并返回成功应答。

关键性质：**回调处理的副作用一次且仅一次**；重复 3 次回调的结果必须与 1 次完全一致。

### 4.2.4 BF-08 超时关单与库存回滚

1. Quartz 每分钟触发（`test` profile 可调整为每 10 秒 / 阈值 1 分钟，便于录屏演示）。
2. 扫描 `status = 0 AND create_time < now - 15min` 的订单（走 `(status, create_time)` 索引），单批处理上限 100 条。
3. 对每张订单执行条件更新 `UPDATE pet_order SET status = 5 WHERE id = ? AND status = 0`；影响行数 0 表示已被用户取消或支付，跳过。
4. 对该订单明细逐条回滚库存 `stock = stock + qty`，写入 `pet_stock_log`（`type=ROLLBACK`）；唯一约束冲突表示已回滚，跳过。
5. 将支付单置为 TIMEOUT（若存在），记录关闭时间与原因。
6. 写运行日志（订单号、回滚明细），供演示与对账。

### 4.2.5 BF-12 商品发布与审核

1. 商家创建商品（含分类、宠物属性、SKU 与库存、图片），初始 `audit_status = 0`（待审）、`status = 0`（下架）。
2. 管理员在待审列表查看商品详情与资质信息，选择通过与驳回。
3. 通过：`audit_status = 2`，商品可被商家上架；驳回：`audit_status = 1`，**驳回理由必填**并展示给商家。
4. 商家修改后重新提交，状态回到待审，形成审核留痕 `pet_item_audit`。
5. 上架前置条件：必须审核通过（BR-13）；下架后前台立即不可见（允许缓存最多 10 分钟陈旧，见 NFR-08）。

## 4.3 订单状态机

### 4.3.1 状态定义

| 状态码 | 名称 | 语义 | 是否终态 | 允许的后续动作 |
|---|---|---|---|---|
| 0 | 待付款 | 订单已创建、库存已扣减，等待支付 | 否 | 支付成功、用户取消、超时关闭 |
| 1 | 待发货 | 支付成功，等待商家发货 | 否 | 商家发货、管理员协助取消（Should） |
| 2 | 待收货 | 商家已发货，等待会员确认 | 否 | 会员确认收货 |
| 3 | 已完成 | 会员确认收货，交易结束 | 是 | 评价（Should） |
| 4 | 已取消 | 用户主动取消或管理员协助取消 | 是 | 无 |
| 5 | 已关闭 | 超时未支付自动关闭 | 是 | 无 |

| 当前 | 目标 | 触发事件 | 操作角色 | 前置校验 | 副作用 |
|---|---|---|---|---|---|

| 0 | 1 | 支付成功回调 | 系统 | 幂等键未使用、金额一致、状态为 0 | 写支付记录、支付时间、订单支付金额 |
| 0 | 4 | 用户取消 | 会员 | 状态为 0、归属正确 | 回滚库存、写 ROLLBACK 流水、记录取消原因 |

### 4.3.3 状态不变量

| 编号 | 不变量 | 校验方式 |
|---|---|---|

**主成功场景**：管理员打开待审列表 → 查看商品与 SKU 详情 → 选择通过 → 系统更新审核状态为通过、写审计记录 → 商家可上架。

**扩展流**：选择驳回但理由为空 → 拒绝提交；驳回后商家修改并重新提交 → 状态回到待审（历史留痕不覆盖）；商品已下架但已被审核通过 → 允许，状态不变。

### 4.6.6 UC-21 商家越权修改商品（安全用例）

| 项目 | 内容 |
|---|---|
| 用例编号 | UC-21-E（异常用例） |
| 用例名称 | 商家修改他人商品被拦截 |
| 参与者 | 商家 B（越权尝试）、系统 |
| 前置条件 | 商家 B 已登录；商品属于商家 A |
| 后置条件 | 请求被拒绝；商品数据不变；审计日志新增一条 |
| 关联需求 | FR-SEC-04、DP-02、BR-21、NFR-12 |

**主成功场景**：商家 B 构造请求 `PUT /api/merchant/items/{A 的商品 id}` → 服务端解析归属 → 判定 `merchant_id` 不匹配 → 返回 403 `PET-2003` → 写审计日志（操作人、接口、目标资源、结果）→ 前端提示无权限。

# 5 功能需求

## 5.1 编号规则与优先级

- **编号规则**：`FR-<模块>-<序号>`，模块取 MEM（会员）、PET（宠物档案）、ADDR（地址）、CAT（分类）、ITEM（商品与 SKU）、SRC（搜索与首页）、CART（购物车）、ORD（订单）、PAY（支付与关单）、FUL（履约）、MCH（商家）、ADM（后台管理）、SEC（安全与审计）、OPS（运维与可观测）。
- **优先级**：M = Must（缺项即不达标）；S = Should（时间允许必做，直接对应加分）；C = Could（有余力再做）；W = Won't（明确不做，见 11.1）。
- **验收标准写法**：采用"可观察行为 + 前置条件 + 期望结果 + 证据形式"，避免"实现良好"这类不可判定表述。

## 6.2 领域模型与 ER 图

领域划分为五个子域：**会员域**（会员、宠物档案、地址）、**商品域**（分类、商品、SKU、图片、审核）、**交易域**（购物车、订单、订单明细）、**支付域**（支付记录、库存流水）、**治理域**（审计日志，复用 `sys_oper_log`）。核心聚合根为订单（`pet_order`），其与明细、支付单、库存流水构成强一致边界。

![图 6-1 领域模型与 ER 图（核心实体及关系）](images/fig-6-1-er.png)

主要关系说明：

- 会员 1 : N 宠物档案、收货地址、购物车行、订单。
- 分类 1 : N 商品（两级分类自关联）；商品 1 : N SKU、图片、审核记录。
- 订单 1 : N 订单明细；订单 1 : N 库存流水（按 SKU 拆行）；订单 1 : 1 成功支付记录（失败支付可多条）。
- 库存流水是库存变化的唯一事实来源，用于对账与幂等校验。

## 6.4 数据库设计约定

| 编号 | 约定 | 说明 |
|---|---|---|
| DB-01 | 命名规范 | 表 `pet_` 前缀 + 下划线小写；字段下划线小写；索引 `idx_`、唯一索引 `uk_` 前缀 |
| DB-02 | 金额类型 | 一律 `DECIMAL(10,2)`，禁止 `FLOAT/DOUBLE`；Java 侧使用 `BigDecimal` |
| DB-03 | 时间字段 | 业务表必须含 `create_time`、`update_time`；统一由服务端生成，不依赖数据库默认时区 |
| DB-04 | 删除策略 | 主数据（会员、商品、分类、档案、地址）逻辑删除；交易数据（订单、明细、支付、流水）不删除 |
| DB-05 | 字符集与引擎 | `utf8mb4` + `InnoDB`，保证 emoji 昵称与事务支持 |
| DB-06 | 索引策略 | 高频查询字段建索引：`order(member_id,status)`、`order(status,create_time)`、`order(create_time)`、`sku(item_id)`、`cart(member_id)`、`item(category_id,status)` |
| DB-07 | 约束兜底 | 库存 `CHECK (stock >= 0)`；金额 `CHECK (price > 0)`；关键业务唯一键必须落到数据库而非仅代码判断 |
| DB-08 | 字段长度 | 标题型字段留足余量；快照字段用 JSON 字符串并限制长度；富文本用 `TEXT` |
| DB-09 | 外键策略 | 业务表之间不建物理外键，由应用层保证引用完整性（利于性能与分库演进），文档中给出引用关系 |
| DB-10 | 初始化脚本拆分 | `db/01_base.sql`（若依基础表）、`db/02_pet_mall.sql`（14 张业务表与索引）、`db/03_seed.sql`（种子数据）、`db/rollback.sql`（回滚） |

## 6.5 数据完整性与一致性规则

| 编号 | 规则 | 保障手段 | 验证方式 |
|---|---|---|---|
| DR-01 | 库存不得为负 | 原子扣减条件 + `CHECK (stock >= 0)` | 并发测试 + 直接 SQL 尝试更新为负值应报错 |
| DR-02 | 同一支付回调只落一条 | `uk_pet_payment_idempotency` 唯一索引 | 幂等测试 |
| DR-03 | 同一订单同一 SKU 的同类流水唯一 | `UNIQUE (sku_id, order_no, type)` | 重复回滚测试 |
| DR-04 | 订单金额等于明细之和 + 运费 | 服务端计算 + 测试断言 | 集成测试 |
| DR-05 | 已支付订单必有支付记录 | 状态推进与支付落库同一事务/顺序保证 | 对账 SQL |
| DR-06 | 订单状态只能按迁移表变化 | Service 层状态机校验 | 状态机单测 |
| DR-07 | 收货信息不随地址修改而变 | 下单快照 | 修改地址后查历史订单 |
| DR-08 | 默认地址唯一 | 设置默认时事务内清除其他默认 | 并发/重复设置测试 |
| DR-09 | 购物车同一 SKU 唯一 | 唯一索引 + 加购 upsert 逻辑 | 重复加购测试 |
| DR-10 | 商品数据隔离 | 查询强制 `merchant_id` 条件 | 越权测试 |
| DR-11 | 删除的商品不可下单 | 可售判定含 `del_flag` | 下架/删除后下单返回错误 |
| DR-12 | 库存流水与库存字段可对账 | 提供对账 SQL：`Σchange_qty = 当前库存 - 初始库存` | 演示时执行对账脚本 |

## 7.5 接口非功能约定

- **幂等**：支付回调必须实现幂等；下单以 `clientToken` 防重；取消/确认收货/发货以状态条件更新实现天然幂等。
- **限流**：登录 5 次/分钟/IP+账号；下单 10 次/分钟/会员；支付回调不做业务限流但做来源校验。
- **超时**：前端 15 秒；后端对外部（沙箱）调用 3 秒；超时不重试非幂等接口。
- **并发**：库存扣减不依赖应用层锁，使用数据库条件更新 + 事务；同一订单的状态变更使用条件更新避免并发覆盖。
- **可观测**：每个响应带 `traceId`；关键接口记录耗时；限流与越权事件单独打点。

# 14 附录

## 附录 A 宠物档案字段与适用性判定规则

### A.1 字段与用途

| 档案字段 | 用途 | 缺失时处理 |
|---|---|---|
| 物种 species | 与商品 `pet_species` 比对 | 无法判定，提示补充档案 |
| 生日 birthday | 推算月龄，与商品 `age_stage` 比对 | 仅按物种与体重判定，提示补充生日 |
| 体重 weight | 与商品 `weight_range` 比对 | 跳过体重判定，提示补充体重 |
| 品种 breed | 仅展示，不参与判定 | 无影响 |
| 绝育 sterilized | 展示与筛选参考 | 无影响 |
| 过敏备注 allergy_note | 详情页风险提示（如"该商品含鸡肉"不做自动匹配） | 无影响 |

### A.2 判定顺序与结论

1. **物种**：商品 `pet_species` 为 `ALL` 或与宠物 `species` 相同 → 继续；否则结论"不适合（物种不符）"。
2. **年龄**：由生日计算月龄；商品 `age_stage` 为 `ALL` 或月龄落在对应区间（JUNIOR ≤ 12、ADULT 13–84、SENIOR ≥ 85）→ 继续；否则"不适合（年龄段不符）"。
3. **体重**：商品 `weight_range` 为 `ALL` 或宠物体重落在区间内 → 继续；否则"不适合（体重段不符）"。
4. 三项全部通过 → 结论"适合"，并展示三条通过原因。
5. 任一字段缺失 → 结论"信息不足，建议补充档案"，同时给出已知项的判定结果。

### A.3 示例

|---|---|---|
| 布偶猫 / 3 个月 / 2.1kg | 幼猫粮，CAT，JUNIOR，0–5kg | 适合（物种、年龄、体重均符合） |
| 布偶猫 / 3 个月 / 2.1kg | 成猫粮，CAT，ADULT，0–5kg | 不适合（年龄段不符） |

| 柯基 / 4 岁 / 12kg | 小型犬零食，DOG，ALL，0–5kg | 不适合（体重段不符） |
| 布偶猫 / 未填生日 / 2.1kg | 幼猫粮，CAT，JUNIOR | 信息不足，建议补充生日 |
